# Production result conflict: bounded isolation

**Status: CODE READY for isolation; production recovery unverified.** This branch does not change a result, provider record, settlement formula, bankroll, betting decision, or production configuration. No deployment has occurred.

## Evidence and scope

`ReconcileFixtureResults.execute()` previously called `persist_result()` outside an item-level error boundary. `ResultPersistenceConflictError` belongs to the orchestrator's fatal invariant set, so one disputed fixture stopped the entire production engine.

Read-only Railway log and PostgreSQL checks on 2026-10-10 identify `api-football:1568827` as the conflicting fixture. The engine crashed after repeatedly fetching result IDs `1568827` and `1574372`; its exception is `result contradicts durable fixture identity`. The durable `fixtures` anchor for `1568827` has home/away team IDs **16246/6938** (Flota Świnoujście / Elana Toruń), recorded with a 2026-09-23 observation. The latest independent `quantlab_fixture_observations.raw_payload`, sourced from `api-football:fixtures` at **08:01:22 UTC on 2026-10-10**, has the same fixture ID and reversed team IDs **6938/16246**, status FT. `1574372` has matching Production and QuantLab team IDs. Thus the exact invariant conflict is a home/away reversal between the durable Production anchor and later provider evidence. Which upstream event first caused the reversal remains unproven; neither side is silently chosen as authoritative for settlement.

At the read-only check, each fixture had one registered pick and zero `fixture_result_observations` or `pick_settlement_events`. This confirms no result/settlement was committed for those two picks at that time; it does not establish the correctness of every historic P&L entry. The disputed pick must remain pending until independently verified evidence supports a separately reviewed correction or void decision.

The change catches **only** `ResultPersistenceConflictError` around `persist_result()`, calls the existing `results` item-failure recorder, logs a payload-free quarantine event with fixture ID, and moves to the next claimed fixture. The repository's transaction context rolls back the disputed observation. The durable failure ledger excludes this fixture from later result claims until an operator, after resolving the conflict, explicitly clears its failure record. It is not silently dropped: the pending acquisition state and one `production_item_failures` row remain. The health counts expose `result_conflicts`, separate from the generic retry count. That fixture never reaches `stable_result()`, pick settlement or CLV. Other invariant errors, including `SettlementConflictError`, remain fatal. `persisted_result_count` now counts successful writes rather than fetched payloads.

The unit regression test reproduces a disputed first fixture and a valid second fixture. Real PostgreSQL integration tests now run the complete `ReconcileFixtureResults.execute()` path with both registered picks: the disputed result rolls back and remains unsettled, one durable failure row excludes it from the next claim, the unrelated pick settles once with matching stake and payout ledger entries, and P&L and readiness counts agree. A second end-to-end test injects a failure into the durable failure-ledger write and requires the entire reconciliation call to fail without a result, quarantine row, or settlement. A repository-level integration test also checks explicit release after clearing the failure in the isolated test database. This establishes local behavior, not 24-hour production recovery.
