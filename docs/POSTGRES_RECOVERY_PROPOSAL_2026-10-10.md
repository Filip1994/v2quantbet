**Issue:** [#247](https://github.com/Filip1994/v2quantbet/issues/247). **Scope:** `sincere-balance` production Postgres only. This document records read-only findings and future operator steps. No backup, bucket, PITR, restore, database write or Railway configuration change was performed.

## What is verified today

At 2026-10-10 17:02 UTC, Railway's read-only `volumeInstanceBackupList` and `volumeInstanceBackupScheduleList` both returned `[]` for the **mounted production** `postgres-volume` instance. `railway postgres pitr status` reports `enabled=false`, and `railway postgres ha status` reports one member with HA off. The database is 19.48 GB (`pg_database_size`); the volume uses about 21.48 GB of its 102.4 GB allocation. The separate `durable-barrel` bucket is used for application cold archive and is not evidence of a PostgreSQL backup. No completed restore test or independently supplied database dump has been identified. Therefore the answer to **“Do we have a verified restorable football PostgreSQL backup?” is NO** on the available evidence. An external copy unknown to this audit cannot be ruled out.

The only application login role found is the PostgreSQL `postgres` superuser. Backup and privilege changes must be sequenced so that a tested recovery point precedes credential/grant migration. A first read-only `pg_stat_wal.wal_bytes` sample near 17:02 UTC was 598,064,706,473 bytes; a second near 19:37 UTC was 599,676,713,317 bytes, with the same 2026-09-26 counter reset. The delta is 1,612,006,844 bytes over roughly 2 hours 35 minutes, or about **15 GB/day if that short interval continued**. This is uncompressed PostgreSQL WAL generated, not measured compressed PITR upload, and a single interval is not a reliable monthly rate.

The currently prepared storage options reuse Railway; an independent off-provider copy remains a separate decision. The owner set an infrastructure budget of at most $40/month, with new spending above the $20 Pro inclusion only where needed. Railway Agent has a separate $0 limit. At the 19:37 UTC read-only check, workspace infrastructure usage was $33.22 with a $33.49 end-of-period estimate and the existing $40 hard limit. With a $2 variance reserve, only about **$4.51/month** is available for added recurring protection at that baseline. Recheck the **workspace-wide** forecast before any activation; do not treat the full $20 as unused credit. Leave the existing hard limit unchanged unless separately approved.

The PITR examples assume 30 days of uploads and 28 days of retained WAL: `30 × GB/day × $0.05 + 28 × GB/day × $0.015`; they are scenarios, not a quote. Railway backups and the PITR bucket remain within one provider, so they do not cover loss of the whole Railway account/provider or malicious deletion with the same access. An off-provider copy would reduce that risk, but it is outside this Railway-only implementation proposal and requires a separate decision. HA improves availability, not backup; it is excluded from this recommendation because it adds steady resource cost and does not solve recovery from deletion or bad writes.

**Current budget implication:** one full 21.48 GB snapshot equivalent costs about $3.22/month, leaving roughly $1.29 under the $4.51 headroom for changed bytes and other variance. At the observed short-interval WAL rate, even an illustrative **5:1 compression** of WAL would imply about 3 GB/day of upload and roughly $5.76/month in WAL egress plus retained bucket storage, **before** base backups and restore compute. This scenario exceeds the present headroom; compression and future WAL rates are unverified. The daily snapshot is the only candidate first step under the current cap, and it still needs a fresh cost check and explicit owner approval.

**Decision rule:** obtain a fresh workspace infrastructure forecast and two read-only WAL-counter samples, estimate PITR compressed traffic with a conservative range, then show the owner the exact proposed schedule/PITR change and maximum plausible added monthly cost. Do not activate a feature if the forecast plus a $2 variance reserve exceeds $40; identify a football-only saving or retain the lower-cost snapshot option and label PITR `BLOCKED/BUDGET`. Recheck usage after the first backup and daily for its first week. If cost rises toward the agreed ceiling, pause further activation and seek approval; never silently delete backups or shut down Production to save money.

## Exact approval and verification sequence

Target objects, to be rechecked immediately before execution: project `c0aa8208-dd61-48c4-a1d8-488802e84f36`, production environment `e08eafba-5581-4ddd-90b7-b0d456ce6cf9`, Postgres service `8053c62b-2ba3-46e8-8bf0-bc5160cb6b9b`, mounted volume `0a1621a8-a176-4816-a38e-9f7b55c89e99`, volume instance `b9a01c7b-7fa7-45cf-a03f-2b13712fc52b`. A Railway GraphQL `volumeInstanceBackupScheduleUpdate` for that instance with `kinds: [DAILY]` is the exact first schedule change; `kinds: [DAILY, WEEKLY]` is a later, separate change. PITR enable targets that Postgres service only. Do not apply either command from this draft document.

1. **Snapshot approval A:** confirm mounted volume ID and existing empty schedule/list again; record DB image, volume use, free space, deployed SHA and a non-peak maintenance window. Approve `DAILY` schedule on that volume instance only. Confirm the first backup has an ID, timestamp, nonzero referenced size, expiry and no error. Add `WEEKLY` only after the first measured cost and separate approval. The schedule rollback is removal of the new schedule; retaining or deleting an already created backup is a separate data-retention decision.
2. **PITR approval B:** confirm budget, DB image compatibility, recent WAL rate, volume headroom and first snapshot status. Approve PITR only for the existing football Postgres service. Railway creates `Postgres-PITR` bucket, sets archive variables and redeploys the database. Monitor DB reachability, archive health, first base backup, latest restorable timestamp and bucket/egress use. If boot/archive fails, stop; do not delete the bucket while it may contain the only new recovery history. Any rollback of PITR configuration and its retention is a separate reviewed action.
3. **Isolated restore approval C:** choose an in-window timestamp and exact temporary cost/window. PITR restoration creates a new sibling Postgres service and volume. Review the staged patch before deployment; do not attach application services or public routing, and restrict inherited variables/access to what recovery needs. No production connection string changes. Verify backup continuity, schema migration version, counts and read-only samples of `registered_picks`, `pick_settlement_events`, `bankroll_ledger_entries`, `quantlab_market_captures` and `quantlab_goal_model_versions` at the chosen time. Record time from restore request to a readable database, latest recovered timestamp, and discrepancies. Pass only if all checks reconcile and no production service used the restored DB. Remove the temporary service/volume only after the owner approves disposal of the test copy.

**RPO/RTO:** scheduled daily snapshots target at most 24 hours of lost writes only while the schedule is healthy; PITR targets the last archived timestamp and can lag during bucket failures. Do not promise a one-hour RPO or a four-hour RTO until archive freshness and an isolated restore drill demonstrate them. The incident runbook must show the actual latest backup/restore point and test duration.

## Emergency stop/go runbook

1. Stop deployments, migrations and replay jobs; preserve the current DB and Railway event/log evidence. Identify the last good write and whether Production picks, settlement or bankroll rows are affected. Treat Research/QuantLab as separate consumers, but do not assume they have separate credentials today.
2. Compare available volume snapshot and PITR restore points. If neither is verified, declare recovery **UNKNOWN**; do not run a blind restore over production. Export, copy or data surgery requires separate authorization.
3. If an approved PITR restore is available, create the sibling only, reconcile immutable pick/settlement histories and freshness, then present an explicit cutover plan. A Git revert cannot undo a committed DB migration or destructive write.
4. Owner approves or rejects cutover. If approved, update only the reviewed connection targets in a release window; check engine, collector, dashboards, modeler and KellyLab health, then monitor the next cron cycles. Keep the original source intact until reconciliation and rollback window end.

**Responsibility:** operator records evidence and exact restore target; repository reviewer checks schema/data reconciliation; owner separately approves paid activation, restore, cutover and disposal. No step in this document grants that approval.
