# Football PostgreSQL privilege separation — draft release design

**Issue:** [#247](https://github.com/Filip1994/v2quantbet/issues/247). **Boundary:** `sincere-balance` production database only. This is a reviewable design, not an authorization to create roles or rotate credentials.

## Confirmed database state (read-only, 2026-10-10)

- `current_user=session_user=postgres`. The only login role is `postgres`, with `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS`. It owns all 79 public tables and all 13 public functions; 54 user-defined triggers exist. There are no public sequences and no custom default ACL rows today. `pg_auth_members` has only PostgreSQL's built-in `pg_monitor` memberships, not application role delegation.
- Railway variable resolution found the same Postgres login/database/password in 16 of 17 non-DB service definitions with `DATABASE_URL`. Application source has no `SET ROLE` or `SET SESSION AUTHORIZATION` call. An application bug or compromised dashboard currently has the database privileges of the Production engine.
- Seven active GitHub-linked services have `python -m h2h.migrate` predeploy; the dormant collector-ACut also has a migration predeploy. Simply changing `DATABASE_URL` to a restricted runtime role would make those deployments fail at migration time. Migration separation is a prerequisite to rotation.

## Service-to-table contract

`S` = SELECT, `I/U` = insert/update, `D` = delete. These are **source-derived required capabilities**, not proof that every code path runs in production. A clone must execute representative paths before any production grant. Any omitted table must fail closed during the clone test and be added by reviewed evidence; do not add `GRANT ALL TABLES` as a shortcut.

## Safe implementation and exact release order

1. **Prerequisites:** prove a restorable football backup under the separate [recovery proposal in draft PR #249](https://github.com/Filip1994/v2quantbet/pull/249). Freeze a list of actual SQL statements and service variables by deployed SHA. Record grants, ownership, predeploy commands, `pg_default_acl`, functions/triggers and pooler mode again immediately before changes.
2. **Offline contract test:** create an isolated disposable PostgreSQL with the same migrations and representative sanitized fixtures, only after infrastructure approval if Railway resources are needed. Define `NOLOGIN` group roles for engine, readers, collector, modeler, KellyLab and archive; explicitly `GRANT USAGE ON SCHEMA public` and `S/I/U/D` on named tables. Deny `CREATE`/DDL and `schema_migrations` to runtime roles. Use `has_table_privilege`, `has_schema_privilege`, `has_sequence_privilege` and real application route/cron invocations. Check negative tests for Production bankroll and pick writes by QuantLab, and archive delete by any non-archive identity.
3. **Migration boundary:** remove migration predeploy from runtime services in a separately approved Railway change. Run migrations once as a controlled release step with a dedicated migrator identity, after reconciling ownership of all current tables/functions/triggers. New migration PRs must enumerate new table/sequence grants; grant updates and code deploy are one reviewed release unit. Do not make the migrator a standing superuser application variable.
4. **Credential rotation:** create separate login identities with secrets stored only in Railway variables; attach one tested group role to each. Rotate one read-only UI first, then KellyLab, then modeler/collector, and engine last. At each step check connection, health, routes or full cron cycle, SQL permission errors, schema migration behavior and data freshness. Keep the previous credential available only for a time-limited rollback window; revoke it after all checks and separate approval.
5. **Rollback:** on a permission failure, stop further rotations and restore only that service's previous Railway variable in an approved window. Do not use a broad `GRANT ALL` to mask the missing query. A role/credential rollback cannot undo schema or data changes. Recheck backup and application health before continuing.

**Stop criteria:** no verified restore, incomplete per-route/per-cycle clone tests, unknown table/function ownership, permission errors, or unexpected data changes. Production role/grant/credential edits, new test database and restore all require separate approval. The present PR contains no executable role mutation because the table-by-table runtime contract has not yet passed an isolated PostgreSQL test; publishing an untested grant script as release-ready would risk Production outage.
